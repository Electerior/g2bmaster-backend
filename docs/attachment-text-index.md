# 첨부 본문 색인 (`bid_notice_document`)

공고 첨부(HWPX·HWP·PDF·XLSX·ZIP)의 **텍스트를 미리 뽑아 두고**, 화면의 "파일 내" 키워드
검색은 그 색인만 조회하는 계통. 구현은 `V20260811171600__bid_notice_document.sql` 부터다.

이 문서의 숫자는 전부 **실측**이다 — 2026-08-11 기준, 색인 45,736건과 실제 나라장터 첨부로 쟀다.

---

## 1. 왜 이 계통인가

원본 모놀리스는 사용자가 "파일 내" 검색을 누를 때마다 **그 자리에서** 첨부를 내려받아 열었다
(최대 300개, 건당 8초 타임아웃, 5개씩 배치). 비용이 두 군데로 샜다.

- 사용자가 기다린다 — 수백 개 PDF·HWPX 를 여는 동안
- 나라장터가 **검색량에 비례해** 두들겨 맞는다

색인은 이 관계를 끊는다. 상류 호출량이 검색량이 아니라 **공고 발생량**에만 비례하고, 검색은
질의 하나가 된다. `bid_notice`(공고 검색 색인)가 세워진 이유와 정확히 같은 구조다.

### 경계

추출 워커는 나라장터 파일 서버를 두드리므로 **적재 계통**에 둔다. 검색 계층에는 주입하지
않는다 — 그 규칙(`notice-search-index.md` §3)이 무너지면 "색인에 없으면 실시간으로 받아오기"
같은 폴백이 검색 경로로 새고, 그 순간 원본의 느림을 그대로 물려받는다.

---

## 2. 무엇을 저장하나 — 파일이 아니라 파서의 출력

`body_text` 에 들어가는 것은 **추출된 평문**이다. 원본 바이트는 저장하지 않는다.

| | 하루 | 1년 |
|---|---|---|
| 첨부 원본 전량 (평균 245KB × 3,643개) | 약 0.9 GB | 약 313 GB |
| 추출 텍스트만 | 약 39 MB | 약 14 GB |

원본이 필요하면 `AttachmentDownloadController` 가 나라장터에서 그때그때 스트리밍한다.
"마감되면 첨부가 내려간다"는 우려는 실측으로 확인되지 않았다 — 7/23~8/03 에 마감된 건을
포함해 표본 103개 URL 이 12일 뒤에도 전부 200 이었다.

파생물이므로 **파서 버전이 데이터의 일부**다(`extractor_version`). 파서를 고치면 원본을 다시
받아 다시 뽑으면 되고, 그 비용(마감 전 8GB)이 원본 보관(313GB/년)보다 훨씬 싸다.

### 못 읽는 파일은 구멍으로 남는다

실측 2,078건 중 **30건(1.4%)**이 텍스트 0자였다(대부분 스캔 PDF). 구멍 자체보다 **구멍이 안
보이는 것**이 문제라, `needs_ocr` 로 표시한다 — 그것이 없으면 화면에서 "그 키워드가 없는
공고"와 "애초에 읽지 못한 공고"가 똑같이 보인다. OCR 은 아직 없다.

## 3. 언제 다시 뽑나

세 신호가 있고, 비용이 다르다.

| 신호 | 감지 비용 | 실측 빈도 |
|---|---|---|
| 첨부 목록 변경(차수 상승 포함) | **공짜** — 적재 응답 안에 있다 | 4일에 2.13% |
| 같은 URL, 내용만 교체 | 다운로드 필요 | 12일에 **0/103** |
| 추출기 버전 변경 | 공짜 | 파서 수정 시 **70건 중 38건(54%)** 이 달라짐 |

두 시점의 입찰공고 6,104건을 비교한 결과가 설계를 결정했다.

```
차수 같음 · 첨부 같음   5,974건 (97.87%)
차수 오름 · 첨부 다름     130건 ( 2.13%)
차수 같음 · 첨부 다름       0건
```

첨부가 바뀌는 일은 **예외 없이 차수 상승을 동반**했다 — 첨부 URL 에 차수가 박혀 있어서
(`bidPbancOrd=000` → `001`) 정정이 나면 URL 이 통째로 바뀐다. 그래서 목록 해시
(`bid_notice.attachments_hash`) 하나로 관측된 변경의 100% 를 잡는다. **재다운로드 기반의
전수 재검증은 넣지 않았다** — 하루 0.9GB 를 쓰면서 잡을 변경이 관측되지 않았기 때문이다.
대신 월 1회 무작위 200건 표본 감사(≈50MB)로 이 전제가 여전히 맞는지 확인한다.

**재추출을 부르는 가장 잦은 사유는 문서 변경이 아니라 우리 파서의 변경이다.**

### 낡은 본문을 즉시 지우지 않는다

첨부가 바뀌면 `documents_indexed_at` 만 NULL 이 되고 옛 본문은 계속 검색에 걸린다. 지금
지우면 정정 순간부터 추출이 끝날 때까지 그 공고가 파일 검색에서 **사라지는 창**이 생긴다 —
"어제 보이던 공고가 오늘 안 보인다" 는 낡은 규격서가 잠깐 걸리는 것보다 나쁘다.
교체는 새 본문이 손에 들어온 뒤 이력 이관과 함께 일어난다.

## 4. 이력

`bid_notice_document_history` 는 대체된 본문을 보관한다. FULLTEXT 도 FK 도 없다 — 검색에
끼면 같은 공고가 여러 줄로 뜨고, MySQL 에는 "현재 행만 색인" 을 표현할 부분 인덱스가 없어
테이블을 나누는 것이 유일하게 확실한 방법이다.

사유는 넷이고, 남기는 시점이 다르다.

| 시점 | 사유 |
|---|---|
| 씨뿌리기 — 목록·차수가 바뀐 것을 안 순간 | `차수상승` · `목록변경` |
| 완료 — 새 본문이 손에 들어온 순간 | `내용변경` · `추출기변경` |

`sha256` 이 그대로인데 텍스트만 달라졌으면 그것은 `추출기변경` 이다. `내용변경` 으로 적으면
나중에 이력을 읽는 사람이 발주기관이 문서를 고쳤다고 오해한다.

## 5. 성능 — 왜 전수 조회가 아닌가

실제 나라장터 첨부 본문으로 27,500행(4.54억 자) 색인을 만들어 쟀다.

| | 27,500행 | 55,000행 |
|---|---|---|
| `LIKE '%서버%'` 전수 스캔 | 3.80초 | — |
| `MATCH ... AGAINST('서버')` | **0.067초** | 0.062초 |
| 실제 화면 질의(EXISTS + 필터 + LIMIT 20) | 0.223초 | 0.436초 |
| 발췌용 상위 20건 본문 읽기 | 0.081초 | 0.067초 |

역색인은 본문을 읽지 않는다. 같은 답에 **57배** 차이가 났고, 데이터가 2배가 돼도 질의는
1~1.7배에 그친다.

### 조심할 것 넷

1. **MySQL 은 FULLTEXT 를 다른 인덱스와 병합하지 않는다.** `MATCH` 가 있으면 FT 부터 돈다 —
   "마감 전만" 같은 조건이 먼저 좁혀 주지 않으므로 **색인 크기 자체를 통제**해야 한다.
2. **`SELECT` 목록에 `body_text` 를 넣지 마라.** 매칭 전체의 오프페이지 읽기가 된다.
   목록은 `EXISTS` 로 존재만 보고, 발췌는 현재 페이지 20건만 2차 조회한다.
3. **콜드 리드가 진짜 위험이다.** 버퍼풀 128MB(기본값)에 FT 보조 테이블 1.6GB 였을 때,
   처음 쏘는 용어가 **8.155초** 였다가 재실행에서 0.140초가 됐다. 운영에서는
   `innodb_buffer_pool_size` 를 최소 2~4GB 로 올린다.
4. **ngram 은 두 글자부터다.** 한 글자 검색어는 색인이 조용히 무시하므로 LIKE 로 떨어뜨린다.

### 색인 구축 비용

| | 실측 |
|---|---|
| FULLTEXT(ngram) 최초 생성 — 27,500행 / 4.54억 자 | 10분 42초 |
| 본문 테이블 | 1.3 GB |
| FULLTEXT 보조 테이블 | 648 MB (본문의 약 0.5배) |
| 인덱스를 건 채로 27,500행 적재 | **29분** |
| 인덱스 떼고 적재 → 생성 | **13분** (2분35초 + 10분42초) |

**최초 백필은 인덱스를 떼고 넣은 뒤 만든다.** 일상 증분(하루 3,643행)은 1~2분이라 이 문제가
없다. 연 용량은 본문 21GB + 인덱스 11GB ≈ **32GB/년**이고, 12개월 롤링으로 통제한다.

> ⚠ MySQL 은 **파티션된 테이블에 FULLTEXT 를 만들 수 없다.** 롤링 정리를 파티션 DROP 으로
> 할 수 없으니 야간 배치 `DELETE` 로 나눠 지운다.

### 이 색인을 읽는 곳은 둘이다

| 읽는 곳 | 쓰는 이유 |
|---|---|
| `GET /api/search/notices` (기본 검색) | 검색어를 공고 텍스트와 **함께** 첨부 본문에서 찾는다 |
| `POST /api/scan-attachments` | 이미 받은 목록의 행에 **발췌(excerpt)** 를 붙인다 |

기본 검색이 첨부까지 보게 되면서 둘의 역할이 갈렸다. **찾는 것은 검색이, 왜 걸렸는지
보여주는 것은 스캔이** 한다. 스캔이 남아 있는 이유는 두 가지다 — 발췌는 본문을 실제로
읽어야 만들 수 있어서 목록 질의에 얹으면 §5 의 2번(`SELECT` 에 `body_text` 금지)을 어기고,
팬아웃 4탭(`/api/bid-announce` 등)은 색인 밖 항목이라 애초에 검색 경로가 다르다.

검색 쪽 질의는 위 표의 `EXISTS` 가 아니라 **`UNION ALL` 두 갈래**다. 공고 텍스트 매치와
첨부 매치를 `OR` 로 묶으면 두 FULLTEXT 중 어느 쪽도 구동 경로가 못 되기 때문이고,
실측과 설계 근거는 `notice-search-index.md` §4.5 에 있다(19.9ms 대 424ms).

## 6. 운영

```bash
# 현황 — 상태별 문서 수, 아직 색인 안 끝난 공고 수, 현재 추출기 버전
curl localhost:8090/api/documents/status

# 추출 한 회차 수동 실행 (앱 키 필요). 남은 일감이 배치보다 많으면 여러 번 부른다
curl -X POST localhost:8090/api/documents/extract
```

주기 실행은 `g2b.documents.enabled` 로 켠다. **기본은 꺼짐** — 여러 인스턴스가 같이 켜지면
같은 파일을 중복으로 내려받는다. 적재와 주기를 나눈 이유는 무게가 다르기 때문이다
(적재는 HTTP 호출 수십 번, 추출은 하루 약 0.9GB 다운로드).

## 7. 알려진 제약

- **입찰 불가 조항 자동 제외는 미이식**이다. `POST /api/scan-attachments` 의 `exclusions` 는
  항상 빈 목록이고, 화면은 아무것도 제외하지 않는다 — 잘못 제외해서 입찰 기회를 지우는 것보다
  안전한 방향이다.
- **파일 내 검색은 색인에 들어온 공고에 대해서만 동작한다.** 팬아웃 검색(`/api/bid-announce`)의
  결과에는 색인에 없는 공고가 섞이므로, 응답의 `notIndexed` 와 화면의
  "N건은 첨부 색인 전(결과에서 빠짐)" 표시로 그 사실을 알린다.
- **DOCX 는 추출 대상이 아니다.** 원본 모놀리스는 지원했다(`lib/files.js`).
- **OCR 이 없다.** 스캔 PDF 는 `needs_ocr = 1` 로 표시만 하고 본문이 비어 있다(실측 1.4%).
- 사전규격 첨부는 **파일명이 없다** — API 가 안 준다. 매퍼가 `첨부1` 처럼 지어내므로 확장자가
  없고, `DocumentSniffer` 가 매직 넘버로 형식을 판정한다. 이 보정이 없으면 사전규격 첨부가
  통째로 색인되지 않는다(첫 회차 200건 중 20건이 그 이유로 실패했다).
